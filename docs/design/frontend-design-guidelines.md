# Ark Tavern 前端设计规范

Ark Tavern 的界面应同时服务于沉浸式故事体验和高密度内容编辑：阅读时让角色与剧情成为主角，管理时让对象、状态和下一步操作清晰可见。视觉可以随皮肤变化，功能含义、操作顺序和数据边界必须保持一致。

本规范适用于前端页面、组件、样式、布局和交互的新增与修改，面向 PC 浏览器与 Electron，不要求手机窄屏适配。下文的“必须／不得”为交付约束，“建议／优先”为默认设计选择。标为“现有”的内容描述当前复用入口，其余为新增和修改界面的要求，不表示现有页面已全部达标，也不要求在局部任务中重构无关页面。

## 设计前先确认范围

1. 阅读 [仓库工作流](../../AGENTS.md)、本规范和 [架构索引](../architecture.md)，定位实际挂载的页面、组件、状态与 API；不能仅因某文件存在就视为可复用功能。
2. 写清目标用户动作、页面入口、主要对象、主操作、数据来源，以及加载、空数据、失败、编辑中和提交中的表现。布局围绕真实功能展开，不为视觉完整虚构按钮、统计或后端能力。
3. 查找同类页面的组件、样式和状态管理方式。局部改动延续所在模块的视觉语言；跨页规则变化同步更新本规范。
4. 用户仅要求设计图或交互预览时，只交付相应产物，不自行改产品代码或真实数据。用户明确要求基于接口重新设计时，以当前接口和本规范为约束，不必照搬旧布局。

产品契约以当前 API、类型与实际挂载链路为准；本规范负责界面表达，不授权修改后端契约。战斗界面还需查阅 [战斗 UI 设计](combat/combat-ui-design.md)，具体尺寸与交互以当前引擎实现为准。历史预览与归档不是新功能已经落地的依据。

## 视觉方向与信息层级

- **内容优先**：首页突出进入与继续体验，聊天页突出叙事和选择，管理页突出查找、编辑与保存。不要把所有页面都做成大标题、统计卡和装饰面板的组合。
- **主次明确**：一个操作区默认只有一个最强视觉主操作。次要操作使用弱化按钮，危险操作与主操作分离。选中、悬停和键盘焦点必须可以区分。
- **克制的氛围**：保留酒馆、终端、角色与世界书的主题感；背景插图、纹理、发光和透明层不能压过正文、降低对比度或阻挡点击。
- **渐进展开**：先呈现完成当前任务所需的信息，再用页签、折叠区或详情展开高级配置。不要把内部字段名、调试输出和整段说明堆在首屏。
- **一致而非同形**：首页可以有更强的品牌表达，管理页保持紧凑，舞台与战斗可以沉浸式呈现；返回、保存、关闭、状态含义仍须一致。

## 主题与颜色

### 现有主题机制

主题类由 `frontend/src/App.tsx` 统一切换，业务组件不自行改写 `<html>` 的主题状态。

| 视觉状态 | 激活条件 | 表达方向 |
|---|---|---|
| 默认深色 | `skin = default` 且 `theme = dark` | 深灰背景、清晰文字与蓝色主操作 |
| 默认浅色 | `skin = default` 且 `theme = light`，使用 `html.light` | 浅底深字，与深色保持相同层级 |
| PRTS | `html.skin-prts` | 深色终端、全息青、克制的线框与切角 |
| 酒馆手札 | `html.skin-tavern` | 纸面与墨色、火漆红、黄铜色点缀 |

PRTS 与酒馆手札自带色板，激活时不叠加 `html.light`。皮肤不改变信息结构、权限或功能，不能出现“某皮肤下才有保存按钮”的差异。

### 颜色复用与修改入口

现有基础颜色定义在 `frontend/tailwind.config.js`，通用样式和浅色覆盖在 `frontend/src/style.css`。以下为默认基准，不是要求所有页面改成同一种背景：

| 用途 | 现有类或色板 | 使用要求 |
|---|---|---|
| 页面与表面 | `bg-gray-900`、`bg-gray-800`、`surface.dark/card/hover` | 沿用所在模块，区分页面、面板和悬停层，不随意叠多层卡片 |
| 分隔与边界 | `border-gray-700`、`surface.border` | 用间距和细边框组织结构，不靠重阴影分隔每个元素 |
| 主操作与选中 | `.btn-primary`、`primary` 色板、既有蓝色工具类 | 主操作用色集中，选中还需边框、文字或标记 |
| 正文与辅助信息 | `text-gray-100/200/300/400/500/600` | 颜色会被主题覆盖；按最终背景验证，不直接假设 Tailwind 默认色值 |
| 危险与状态 | `.btn-danger`、红／黄／绿状态色 | 危险、警告、成功须配文字或图标，不只靠颜色传意 |
| 战斗语义 | `combat.*`、`class.*`、`dmg.*` | 玩家／敌人、职业、伤害类型颜色保留各自含义，不借作普通装饰色 |

新增样式优先使用已有类和模块变量，不能在每个组件内散落一套硬编码色值。确有新的语义颜色时，在对应模块统一定义并覆盖适用主题；动态角色色属于数据驱动例外，但要保证可读性。说话人姓名沿用 `.dlg-name` 与 `--role-color` 的色相保留、明度调整方式，不直接把原始角色色当正文颜色。

### 皮肤的硬边界

- `frontend/src/styles/skin-prts.css` 与 `skin-tavern.css` 中的颜色工具类生成区由 `scripts/gen_skin_utils.py` 管理。修改该区颜色映射必须改脚本色板后执行 `python scripts/gen_skin_utils.py`，不得手改生成区。
- 新增颜色工具类后也要检查皮肤是否覆盖；需要时重新生成并审查差异。响应式、任意值和未支持变体不能假定会被脚本自动覆盖。`--check` 只报告扫描与规则条数，不是文件同步或视觉正确性的验证。
- 生成区之外的组件样式、纹理与语义变量在所属 CSS 中维护，不能借调整配色擅自重构整套主题机制。
- PRTS／酒馆覆盖使用 `@scope (html.skin-*) to (.bg-combat-bg)`。**战斗页不换肤**；新增覆盖不得穿透该边界。弹出层若挂到 `body`，需特别验证是否脱离原有主题边界。
- 是否属于战斗页看渲染位置，不看文件夹名称。例如世界书中的剧情节点图虽位于 `components/combat/`，仍属于需要换肤的管理界面。

## 排版与尺寸

### 字体与阅读

现有正文使用系统无衬线与中文回退字体；Tailwind 的 `font-body` 为 Noto Sans SC，`font-display` 为 Orbitron，`font-mono` 为 JetBrains Mono。展示字体仅用于品牌、短标题或数值，不能铺满中文长文；字体不可用时，回退字体也必须保证可读和布局稳定。酒馆皮肤可沿用其衬线表达。

| 层级 | 默认选择 | 约束 |
|---|---|---|
| 辅助标签与元数据 | `text-xs`，13px／18px 行高 | 这是项目覆盖后的值，不是 Tailwind 默认 12px；不承担长段正文 |
| 表单、列表与一般 UI | `text-sm`，15px／22px 行高 | 新增密集界面优先从此档开始，不能靠普遍缩小字号容纳内容 |
| 阅读正文 | `text-base`，16px；行高建议 1.6–1.8 | 中文长文限制行宽，保留段间距，不在超宽屏拉成整行 |
| 分组与页面标题 | 建议 18–24px，500–600 字重 | 首页品牌可例外；同页标题层级应少而明确 |

长名称应允许换行或省略后查看完整内容，不能撑开按钮与列表列宽。ID、路径和连续英文要有溢出策略；数量、时间与资源消耗需要对齐时使用等宽数字。正文不使用大段全大写、拉大字距或装饰性渐变字。

### 间距与形状

新增区域以 4px 为基础步进，优先使用 4／8／12／16／24／32px。相关元素紧凑，分组间距大于组内间距；页面内边距建议 16–24px。现有 `.btn`、`.input` 使用 `rounded-lg`，`.card` 使用 `rounded-xl`，默认分别为 8px、12px；PRTS 等皮肤的切角或直角覆盖应保留，不在局部强制恢复圆角。

普通按钮和输入框建议保持 36–40px 左右的可点击高度；紧凑工具按钮也应提供至少 32×32px 的操作区域，不能仅让 16px 图标本身可点击。复选框、单选框可以视觉较小，但标签应一起可点击。上述为桌面交互基准，不用于改变战斗地图、卡牌等专用尺寸。

## PC 布局与窗口适配

- 默认验证 1366×768 和 1920×1080 的桌面视口，至少覆盖一个常见窗口尺寸；低高度密集页面可补充 1280×720。记录实际视口与缩放，不把屏幕物理分辨率等同于 CSS 可用区域。
- 管理页优先采用“导航或列表 + 主工作区 + 按需详情”的布局。主操作和保存状态应在对应工作区内稳定可见；辅助面板挤占主内容时允许折叠或调整宽度，不缩小整页字体。
- Flex／Grid 中明确可伸缩区域，必要时使用 `min-width: 0`、`min-height: 0`。主内容可滚动，标题、工具栏与底部操作不能被挤出窗口；避免页面和内部面板同时出现难以预期的多层滚动条。
- 桌面窗口变窄时，优先让工具栏合理换行、次要信息收起和列表局部滚动。表格、节点图、地图可有明确的局部横向滚动或缩放，普通页面不应整体横向溢出。
- 长表单、详情弹窗限制最大高度并让内容区滚动，关闭和确认入口保持可达。宽屏增加阅读留白或编辑空间，不把文字无限拉长。
- 涉及文字、固定高度或弹窗的改动，检查桌面浏览器缩放后的可操作性；建议覆盖 125% 或 150%。无需额外实现手机导航，也不以手机窄屏截图作为交付门槛。

## 组件与交互

### 现有复用入口

| 场景 | 入口 | 用法 |
|---|---|---|
| 通用按钮、表单与卡片 | `style.css` 中 `.btn`、`.btn-primary`、`.btn-danger`、`.btn-ghost`、`.input`、`.checkbox`、`.card`、`.panel-title` | 优先组合既有类；这是 CSS 基元，不是已存在的 React Button 组件库 |
| 图标 | `components/AppIcon.tsx` | 统一 Lucide SVG 映射，24×24 viewBox、默认显示 16px、描边 1.8、`currentColor` |
| 品牌标志 | `components/TavernMark.tsx` 与 `frontend/public/logo.png` | 复用当前资源，不用文字、Emoji 或新绘制标志替换 |
| 确认交互 | `stores/confirmStore.ts` 的 `confirmAction()`、`components/common/ConfirmDialog.tsx`、`GlobalConfirmDialog.tsx` | 复用统一确认入口与安全默认焦点，不另建一套全局确认状态 |
| 长文本渲染 | `components/MarkdownRenderer.tsx` | 保留统一的 Markdown 表达与安全边界，不为新页面自行注入未经处理的 HTML |
| 面板宽度与拖动 | `hooks/useResizableWidth.ts`、`components/common/ResizeHandle.tsx` | 先检查是否适合当前布局，再复用既有边界和交互 |

上表中 `components/`、`hooks/`、`stores/` 均相对于 `frontend/src/`。新增跨页模式前先查调用点；单页样式放入该模块，确有复用再抽取共享组件，不为了规范引入另一套 UI 框架、图标库或动画依赖。

### 按钮与表单

- 操作文案使用“动词 + 对象”，如“创建会话”“保存修改”“移出阵容”。删除、移除绑定、关闭和放弃修改不能混用同一措辞。
- 提交中显示明确状态并防止重复提交，成功后再更新已保存状态。禁用控件须有可见原因，不能只通过悬停禁用按钮才能发现原因。
- 字段有持续可见的标签，提示说明格式与作用范围，错误就近显示并与字段关联。占位符不代替标签；必填、合法值和依赖关系在提交前可理解。
- 搜索无结果与“尚无数据”分开呈现，前者给清除筛选入口，后者给有权限执行的创建或导入入口。列表刷新保留合理的选择与滚动位置。
- 页签表达同一对象的不同视图，筛选表达列表条件，不让外观相同的控件承担截然不同的语义。切换后保留必要上下文，不能静默丢弃草稿。

### 弹窗与危险操作

弹窗只用于明确、局部的任务。长流程优先页面或向导，避免在多层弹窗间编辑同一个对象。普通弹窗必须有可理解的标题、关闭方式、键盘焦点管理及关闭后的焦点归还；Esc 与遮罩关闭是否允许应遵循该任务的数据保护要求，不得绕过未保存确认。背景区域在模态任务期间不可误操作。

必选流程不能套用“随时关闭”的规则。例如战前简报可以最小化，但不能关闭跳过，最小化后仍保留输入与推进限制。应明确说明如何完成流程；最小化、取消和提交是不同动作，不得在整理弹窗样式时互相替代。

删除、覆盖、重置、回档等不可轻易撤销的动作，确认前说明对象、影响范围和不可恢复后果，默认焦点放在安全动作。不要在前端先显示“已删除”再等待服务端拒绝。普通确认复用项目样式，不新增 `window.confirm`／`alert` 的平台割裂体验。

编辑页区分“有未保存修改”“保存中”“已保存”“保存失败”。失败或版本冲突保留用户输入并说明恢复方式，不能自动用远端数据覆盖草稿，也不能把本地预览标为已保存。

### 异步状态

每个数据驱动区域在设计时都应检查以下状态；不适用项注明原因，不用正常截图代替状态设计。

| 状态 | 界面要求 |
|---|---|
| 首次加载 | 占位或简洁进度说明，避免先闪“空数据”；不伪造百分比 |
| 空数据／无搜索结果 | 解释当前范围与下一步，不填入看似真实的示例资产 |
| 后台刷新 | 尽量保留已有内容，显示局部忙碌状态，不反复遮住整页 |
| 请求失败／断线 | 错误信息与重试入口可见，保留输入，区分配置问题与服务不可用 |
| 提交与完成 | 防重复操作，只有确认落盘后才显示成功；结果与当前对象对应 |
| 切换对象／过时响应 | 旧请求不得覆盖新对象，不串会话消息、错误和保存状态 |

## 产品页面的专项约束

### 首页与管理工作台

首页现有入口为会话大厅、角色、世界书、文档和设置；有可恢复战斗时显示“继续战斗”。重排首页时保留后端／LLM 状态和 BGM 静音、音量控制，不用假统计替代实际状态。音频启动遵守用户手势与浏览器策略。

世界书、角色与会话编辑始终说明当前对象及修改范围，尤其区分全局内容、世界书定义与当前会话的覆盖。书架为空是合法初始状态，不假定预装世界书、角色或示例会话存在。剧情世界书与资料库不能仅为了统一外观而失去用途区别。

会话的 `combat_mode` 在创建时确定，不能在后续详情页设计成可切换设置。界面中的绑定、保存、预览与继承状态必须对应真实接口含义，不能把“未绑定”显示成“加载失败”。

### 对话与舞台

旁白、角色台词、玩家输入、系统提示和 LLM 错误必须有清晰区分。LLM 失败显示结构化错误与恢复动作，绝不伪装成模型回复。说话人以真实署名和角色信息为准，不能仅为视觉完整而补一个不存在的角色。

流式输出不得反复抢焦点或强制把正在回看历史的用户拉到底部；自动滚动跟随用户是否仍处于最新内容附近。中文输入法组合输入不能触发发送，发送快捷键应有提示并遵循现有输入模式。取消、继续、重试只能在接口支持的语义下提供，不把“停止等待”冒充“服务端已撤销”。

舞台中的角色立绘、背景、字幕和选择区应分别承担角色识别、场景氛围、阅读和决策。长选项使用可滚动区域，出现选项时不应把关键字幕或主操作挤走；自由输入与查看记录的入口不因装饰而丢失。装饰动画不能妨碍文字选择、键盘输入或推进剧情。

### 战斗与节点图

战斗 UI 优先说明当前回合、行动资源、选择对象、合法目标和结算结果。颜色配合形状、图标与文字表达敌我和可操作性；特效不得覆盖关键状态或把后端尚未确认的动作呈现为最终结果。默认深色战斗视觉与外壳皮肤隔离，具体地图、卡牌和横版呈现遵循对应引擎。

节点图与高密度画布应提供可发现的选择、缩放和定位方式，区分当前、选中、可达与不可达状态。画布可以缩放，工具栏、属性编辑和提示文字仍应可读；不要为统一布局改变节点、分支或战斗规则。

## 可访问性与资源

- 优先使用原生 `button`、`input`、`select` 和语义结构；不能只给可点击 `div` 加鼠标事件。主要流程可通过键盘完成，焦点顺序与视觉顺序一致。
- 所有交互元素提供清晰的 `focus-visible` 状态。现有基础输入样式移除了原生 outline，新增或修改控件必须确认有有效的焦点替代，不能假定浏览器会补上。
- 图标按钮在按钮上提供 `aria-label` 或可见文字。`AppIcon` 默认隐藏于辅助技术，单独放入图标不构成可访问名称；tooltip 也不能成为唯一说明。
- 普通文字与背景对比度至少 4.5:1，大字至少 3:1（约 24px 常规或 18.7px 粗体），关键控件边界与焦点等非文本信息至少 3:1。对比度按实际皮肤、透明度和图片背景测量，不能仅看色板。
- 错误、成功、选中和禁用不要只靠红绿或透明度表达。重要异步反馈通过适当的状态区域提示；流式正文不逐字触发屏幕阅读器播报。
- 图像提供稳定尺寸与缺失回退。装饰图使用空替代文本，有意义的角色／资源图提供名称；裁切保留人物识别部位，不能拉伸立绘。媒体与字体沿用项目资源路径，不引入无必要的外部下载依赖。
- 普通控件过渡建议 150–300ms，主要动画优先使用 `opacity`／`transform`。尊重 `prefers-reduced-motion`，关闭非必要循环和位移动画；PRTS／酒馆氛围层保持静态，不移植预览稿的持续闪烁特效。
- 长列表、图片、流式消息与画布按需加载和更新，避免在渲染中扫描整库或让每个字符更新整页。性能优化不能以丢失信息、草稿或状态准确性为代价。

## 实现与验收清单

代码和交互改动应完成以下检查；纯文档改动只需核对来源、链接、术语与差异，不因本清单要求重跑无关 UI 测试。

- [ ] 页面入口、主要操作、数据范围与当前 API 一致，无假按钮、假状态或新增产品契约。
- [ ] 复用已有样式、图标与组件；新增规则有明确归属，未改皮肤生成区、未污染战斗边界。
- [ ] 在受影响页面检查默认深色、默认浅色、PRTS 和酒馆手札；共享样式改动抽查首页、管理页、聊天及战斗边界，不要求不存在的“皮肤 × 明暗”组合。
- [ ] 桌面视口、常见窗口与相关缩放下，长名称、长正文、空数据、多条目、滚动和弹窗均可用；不要求手机窄屏验证。
- [ ] 检查悬停、焦点、选中、禁用、加载、失败、保存中与未保存状态；键盘能完成主要流程，中文输入不误发送。
- [ ] 删除／回档／覆盖的影响范围准确，取消不产生提交，失败保留草稿，异步响应不串对象。
- [ ] 在 `frontend/` 执行 `npm run build`；按改动范围运行已有 UI 逻辑与组件脚本。涉及后端或公共契约时执行 `bash scripts/run_tests.sh` 或 [工程笔记](../notes.md) 中的本机等价入口。
- [ ] 在实际桌面浏览器验证布局、交互和控制台；涉及 Electron 专有行为时补充 Electron 验证。构建、SSR 或 API 测试不替代浏览器验收，浏览器通过也不等于 Electron 通过。
- [ ] 验收使用隔离数据／模拟 API，先确认页面不会触发真实续写、保存或消耗 LLM。不得擅自重启用户正在使用的服务或改真实存档；确需操作时先获确认。
- [ ] 交付说明修改范围、测试命令与结果、浏览器视口／主题／数据方式、未验证项。浏览器不可用时给出可复现的验收交接，不声称视觉验收完成。

规范与实际实现发生分歧时，先辨明是实现缺陷、文档过时还是新的设计需求；只修正任务范围内的部分，并同步相关规范。工程环境差异、已知未修项与复现方式记录在 [工程笔记](../notes.md)，不把一次性验收日志写入长期设计规则。
