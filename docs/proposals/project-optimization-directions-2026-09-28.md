# Ark Tavern 项目优化方向

日期：2026-09-28

状态：方向建议，尚未进入实施；优先级不代表已经排期。

## 核心判断

下一阶段最值得优化的，不是功能数量，而是让已有能力组成可靠、好上手、能持续产出内容的完整体验。

建议遵循：**作者决定关键事实，AI 丰富过程，程序落实后果。**

推进顺序：可靠的完整冒险 → 外部用户独立开局 → 外部作者独立交付作品。

## 分析依据与边界

- 本文整理自本次项目优化讨论，依据当前架构文档、项目问题记录及部分源码的静态检查。
- 已查看叙述与大纲、会话回档与快照、战斗结算、世界书工作台和 Electron 打包配置等相关实现；不构成完整代码审计。
- 没有运行测试、构建、真实模型评测或实际试玩，不能把文档中的已实现能力视为运行质量证明。
- 项目问题记录中的缺口需要在实施前重新复现；没有玩家留存、作者效率或成本基线数据，收益判断属于待验证假设。
- 历史产品讨论仅作背景；项目现已是通用世界书平台，不应沿用旧的方舟专用定位、自动安装假设或已经移除的 AI 依赖构建方案。

## 1. 最高优先级：选择与后果的可靠性

现有基础包括剧情分支、回档、战斗结算和状态快照。重点应是补齐这些机制之间的闭环，而不是另起一套状态系统。

### 现有信号

[项目问题记录](../notes.md)的“剧情验收中仍未修的缺口”列出了开场泄露后续章节、叙述不自动提交任务状态、最后节拍缺终态等问题；“灰灯渡口”记录还指出战前绕行缺结构化结算、结局事实仍受模型一致性限制。以上均需重新复现确认。

### 建议

- 任务完成、关键人物生死、物品获取和路线选择，由结构化状态确认，不只存在于叙述文本中。
- 战斗、谈判和绕行都能产生正式结算，避免只有打赢才算推进。
- 回档同步恢复任务、角色数值、分支及知识范围。
- 剧情拥有明确结束状态，结束后不能继续误推进。
- 区分世界事实与角色知识，降低后续剧情和秘密提前泄露的风险。
- 对重试、刷新与重复请求验证幂等性，避免重复奖励或重复推进。

### 验收

同一短篇分别走不同路线，执行刷新、重载、回档和失败重试，关键事实、资源与结局始终一致。将确认的问题变成可重复的回归用例。

## 2. 用一个完整短篇牵引优化

下一轮推荐目标：做出一个 30–60 分钟、无需开发者现场解释也能完成的示范冒险。

这不是增加一批内容，而是用一个作品检验平台的完整体验。

### 最小内容范围

- 一次有明显后果的选择。
- 一条非战斗解决路线。
- 一场有叙事意义的战斗。
- 至少两个真正不同的结局。
- 中途退出、恢复与回档。
- 完整的背景、角色、音乐和结局反馈。

保持用户显式安装示例的现有原则，不恢复自动安装内容。

### 验收

邀请少量目标用户独立试玩，记录卡住的位置、人工解释次数、完成情况、等待感受及选择后果是否清晰。先形成基线，再设定改善目标，不以资源数量代替可玩质量。

## 3. 创作工具：从管理数据转向完成作品

世界书、角色、节点图和演出资源已有基础。下一步应降低作者把它们串成完整作品的成本。

| 作者的问题 | 建议能力 | 验收方式 |
|---|---|---|
| 还缺什么才能发布？ | 检查入口、角色、资源、分支落点和结局完整性 | 错误能定位到具体内容并给出修复路径 |
| 为什么设定没出现？ | 基于现有 Prompt 预览解释未载入原因 | 解释与实际注入链路一致 |
| 改大纲会影响什么？ | 展示失效节点引用、演出绑定和旧会话影响 | 更新前能预览影响，不静默破坏引用 |
| 只想测试这一幕 | 从指定节拍创建隔离测试会话 | 不污染正式存档，测试前置状态明确 |
| 别人能否完整打开作品？ | 在干净环境检查整书资源与依赖 | 无作者本机隐藏资源也能打开和游玩 |

当前 `WorldBookManager.tsx` 明确保留“依赖配置编辑 UI 未挂载、保存条实际不可达”的说明。需要先判断哪些能力应通过简单入口重新暴露，哪些留作高级能力，而不是直接恢复旧的复杂界面。

不建议直接恢复已移除的 AI 自动猜依赖功能。优先投资可解释的检查与可控的辅助操作。

## 4. 降低首次使用门槛

当前 README 说明项目只能从源码运行；Electron 构建配置仅列出前端与 Electron 产物。配置打包目标不等于已经具备独立运行的安装包。

### 建议

- 先专注 Windows，提供自包含运行包或经过干净机器验证的安装流程。
- 首次启动检查后端、模型连接和可写目录。
- 模型测试不仅检查连通，还验证结构化输出能力。
- 明确区分“开始游玩”和“创作世界”两条入口。
- 使用作品声明的合理默认值，减少从选作品到第一轮的配置负担。

体验设计按任务区分：玩家界面突出故事和行动，作者界面按需展开配置复杂度。无需因此立刻整体重做视觉。

### 验收

在没有开发环境的机器上验证安装与开局；记录首次成功开局耗时、开局成功率和需要人工解释的次数。

## 5. 性能优化先测每一轮

当前叙述链路包含文本生成、结构化提取，以及可能发生的偏离检测。用户体感慢不一定来自前端渲染。

### 先建立指标

- 点击发送到首字出现的时间。
- 叙述结束到选项可操作的时间。
- 每轮模型调用次数、输入与输出 token。
- 重试和降级比例。
- 整段冒险的耗时与费用。

### 再选择优化

依据数据调整偏离检测触发条件、上下文预算、缓存复用和可安全并行的步骤。保留常驻稳定层与触发动态层的既有注入纪律。

界面应区分“故事正在生成”和“结果正在确认”。不要为了快而提前提交未经校验的状态。

### 验收

使用固定场景和可比模型配置比较优化前后数据，同时确认分支、状态与错误处理没有退化。

## 6. 工程优化围绕高风险链路

暂不建议整体换框架或大规模重写。

### 建议

- 建立固定的剧情状态测试和真实模型评测用例。
- 将已确认的严格 `xfail` 缺口逐个转成真正通过的测试。
- 建立测试、构建和关键浏览器流程的自动化门禁。
- 验证流式响应、切换会话、失败重试与回档交错时的状态一致性。
- 随功能修改拆分高耦合模块，不以文件变短作为主要目标。
- 对内容更新、资源缺失和存档兼容提供明确检查与恢复路径。

程序测试回答“状态是否正确”；真实模型评测回答“是否遵守设定、保留玩家选择”。两者不能互相代替。

## 推荐阶段与投入取舍

| 阶段 | 主要交付 | 放行依据 |
|---|---|---|
| 第一阶段：可靠的完整冒险 | 一个精品短篇及关键状态缺口修复 | 不同路线、终局、恢复和回档可重复验收 |
| 第二阶段：独立开局 | Windows 分发与首次使用流程 | 外部用户无需开发者协助完成安装和开局 |
| 第三阶段：独立创作 | 发布检查、局部试跑、完整分享与更新检查 | 外部作者不改代码即可交付可玩的作品 |

性能测量和关键回归门禁应贯穿各阶段；具体性能优化由测量结果决定。

暂缓新增战斗体系、大规模视觉翻新、社区市场和全面架构重写。它们并非没有价值，但目前不能直接解决最关键的体验问题。

若只选一个下一轮主题：**以精品短篇为验收载体，补齐选择、结算、终局与回档的可靠性。**
