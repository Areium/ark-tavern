# 《灰桥回声》完整剧情设计

状态：**审阅候选，未注册到正式内容库**。这是泰拉背景的原创支线，不是官方剧情复述。
本次完成设计和验收；没有改动运行时来实现自动任务、结局锁或护送系统。
测试结果、问题与修复顺序见 [验收报告](../../qa/2026-09-20-story-audit.md)。

## 体验目标与入口

玩家作为博士，协调罗德岛医疗小队查明一则延迟广播，在有限供电下完成撤离并交代责任。
冲突来自技术故障、管理失误与不同群体的恐惧，不靠追加隐藏反派或一次检定决定生死。

- 规模：5 章、12 节拍、4 条主线任务、1 条支线任务、2 场可避战遭遇、3 个互斥叙事结局。
- 开场：灰桥临时救护站，傍晚，低云、潮湿、电台杂音；名册上仍有七人未撤离。
- 推荐阵容：阿米娅、临光、能天使、闪灵；实际阵容以玩家明确选择为准，未入队角色不自动发言。
- 剧情 ID：`qa_greybridge_echoes`；世界书：`arknights`。
- `narrative` / `tactical` 在创建会话时选定，不在中途切换。

## 完整主干及每步验收条件

以下条件是设计与人工验收口径，不是已经实现的自动状态规则。可执行正文在
[plot.md](plot.md)，机器可核对的 ID 清单在 [manifest.json](manifest.json)。

| 章 / 节拍 | 玩家要做什么 | 可选行动及代价 | 到下一节的必要事实 |
|---|---|---|---|
| 1 / `beat_gb_arrival` | 核对广播、机械钟、七人名册 | 询问候车人 / 查时间戳 / 对行李牌 | 确认有人未撤离，广播不能直接当作事实 |
| 1 / `beat_gb_triage` | 初步安置并分工 | 先救治换信任；先抄录保时间戳；分组需联络 | 七人均有人照料，确认机房维修员线索 |
| 2 / `beat_gb_witness` | 取得搬运工证词 | 署名须征得同意；匿名也可继续 | 分清“改过排期”与“破坏设备”不是同一事实 |
| 2 / `beat_gb_manifest` | 对照药品与行李清单 | 交换伤员名单 / 要求归还物资 | 截药责任与广播事故分开调查 |
| 2 / `beat_gb_gate` | 通过封锁线 | 交换名单避战 / 掩体间突破 / 叙事绕行 | 得到维修通道线索；胜、避、退不能混写 |
| 3 / `beat_gb_power` | 测线路、找维修员、核实供电限制 | 测试失败可用机械记录补证 | 电池不足以无限供电，不凭空“全部修好” |
| 3 / `beat_gb_signal` | 交叉核对原始录音、排期单、证词 | 三条中任两条解释事故，第三条提高追责完整度 | 区分熔断故障与用旧录音隐瞒，确认临停列车窗口 |
| 4 / `beat_gb_choice` | 确认供电与撤离方案 | 救护站优先 / 广播优先 / 分段供电；各自有明确代价 | 玩家确认后执行，不替玩家决定、不杜撰额外电量 |
| 4 / `beat_gb_defense` | 化解道路冲突、等待医疗车 | 用名单澄清 / 两波战斗 / 撤退走小道 | 从实际结算或避战结果继续；失败不封死剧情 |
| 4 / `beat_gb_evacuation` | 点名并交接人员、证据 | 优先人员 / 护证据 / 退出危险区 | 七人逐一有去向；未救者进入待救名单 |
| 5 / `beat_gb_hearing` | 复核责任和三次关键选择 | 公开事实 / 保护身份 / 提交罗德岛复核 | 只引用取得的证据，让玩家纠正记录 |
| 5 / `beat_gb_epilogue` | 选择与记录一致的一个结局并告别 | 不再新增敌人或任务；主动询问才后日谈 | 人员、证据、代价三项交代清楚；结局唯一 |

主干顺序不依赖胜利。取证顺序、救治优先级和署名选择可以变化，必要线索保留替代来源。
“绕行”和“败退后继续”目前是叙事设计：两份战斗 JSON 仅显式提供 `assault` 与 `negotiate`
两种打法，不把正文中的每个建议描述成已存在的按钮。

## 任务与叙事记录

| ID | 任务 | 触发 | 收束依据 |
|---|---|---|---|
| M1-1 | 确认仍在等待的人 | 到达救护站 | 核实名册并完成初步救治 |
| M2-1 | 还原二十分钟 | 到达桥头 | 至少两条独立证据吻合；缺证不阻断救援 |
| M3-1 | 只够一次的电量 | 找到维修员 | 供电选择经确认，联络得到回应 |
| M4-1 | 每个人都要回应 | 医疗车接近 | 已救、待救、交接对象逐人记明 |
| S1-1 | 保留姓名的权利 | 取得证词 | 同意署名，或保留匿名复核渠道 |

建议未来状态层记录 `known_people`、`evacuated_people`、`pending_rescue`、`evidence_ids`、
`witness_consent`、`power_plan`、两次 `encounter_result` 和 `ending_id`，由持久化事实派生结局。
这些是修复方案，不是当前 JSON 解析器支持的新字段。当前只可人工管理任务状态；
LLM 文字写“已完成”不会自动完成任务，文字写“获得物品”也不等于已经入包。

## 互斥结局与失败回路

结局判定顺序先检查 C，再检查 A，剩余完整救援归 B，避免条件重叠。

| 结局 | 设计条件 | 必须交代的代价 |
|---|---|---|
| C：留给下一班车 | 本次撤离不完整，或行动终止且仍有人待救 | 明确待救名单、预警与下一次救援责任人，不能写“圆满完成” |
| A：仍有人回应 | 撤离完整、至少两条证据保全、共同记录获各方确认 | 解释供电取舍和现场冲突，不把救援写成无成本奇迹 |
| B：没有署名的灯 | 撤离完整，但证据或共同确认不足；包含保护身份的路径 | 人先获救，追责需后续调查；保护匿名不等于否定证词 |

检定失败用另一来源补足必要线索；谈判失败可战斗或绕行；战斗败退进入小道并影响救援完整度。
玩家选择撤退但最终全员已交接时，应依据实际人员状态判定，不仅凭一个“撤退”按钮锁定坏结局。
当前程序没有正式终态锁，也没有自动结局条件执行器，三结局仍需人工审阅叙事是否一致。

## 战斗候选与验收

| 节点 | 设计意图 | 编排 / 威胁 | 实测摘要 |
|---|---|---|---|
| [enc_gb_gate](battles/enc_gb_gate.json) | 让首次武装冲突可交涉，也可利用掩体接近 | 7×7，墙与掩体，2 名士兵；3.2 / T1 | standard / low 各 30 种子；胜率均 100%，中位 4 / 5.5 回合，血损 3.7% / 12.7% |
| [enc_gb_evacuation](battles/enc_gb_evacuation.json) | 两波压力下保留医疗与移动 AP，结束后清点 | 7×8，掩体、火场、高地；2+2 敌人；5.8 / T1 | standard / low 各 30 种子；胜率均 100%，中位 7 / 8 回合，血损 5.4% / 14.4% |

两节点结构校验通过，共 120 次模拟。无首回合清场，移动 AP 非零；但是普通战的压力偏低，
不满足“最终难度已调好”的结论。先调站位、波次和编成，再考虑数值；不能为方便验收改引擎。
模拟的 `standard` / `low` 是工具预设队伍，不等同于四名推荐角色的整套存档装备。

撤离关声明预算已从 6.4/T2 校正为实际 5.8/T1；早期 standard 报告保留旧声明，详见验收报告。
节点没有独立护送单位、路线倒计时或协商前置条件校验。奖励仅以实际战斗结算为准；
`急救包` 的平铺文档读取存在已复现兼容问题，不能据这次模拟宣称它已在全链路正确发放。

## 上线前的验收门槛

1. 先修验收报告中的叙述保存、开场边界、阵容恢复、任务与终态、分支恢复问题。
2. 用真实模型走完完整主干；另测救援优先、证据不全、败退三条结局路径，不能用脚本化模型代替。
3. 对两节点重新审阅普通战压力，补测真实战斗胜利→结算→重复请求→继续剧情的幂等链路。
4. 浏览器 / Electron 人工验证向导、选项、变体、任务面板、剧情树、战斗拖放与音画。
5. 经内容人工审阅后，才把 `plot.md` 安装为 `data/plots/qa_greybridge_echoes/index.md`，
   并把战斗 JSON 加入 `data/combat/nodes/`；正式写入前复查 ID 冲突、校验和模拟。

目前只在测试的临时数据根目录安装候选，不改用户存档、正式剧情或全局世界书。
